I moved the pin to the other project's core (arman-vpn-client 1.0.12) and used its sign-in API: that is copying their code, not taking an idea, and its messages said "Arman VPN" (the owner saw "...Sign in with the browser in the Arman VPN app instead"). Reverted: `native/fxvpn.pin` is again `e9e6c49` (firefox-vpn-client), CI fetches that repo, host/main.go as before.

## Evidence that decides what to build (owner's log, 6/7 Nov, 1.14.0 core)
Even with that core's Firefox TLS hello and its OAuth-code fallback: `POST /v1/oauth/authorization` (session Hawk) answers 406 after every one of 5 solved challenges (`challenges=pat,pow,clientmetrics rounds=2`, the solver's page probe on accounts.firefox.com passes). So (a) the TLS hello was not the whole story, (b) the refusal is not specific to `/oauth/token`, (c) solving the site's challenge does not unlock the API host's /oauth/* routes. Earlier: the WebView's own `fetch` (Chrome TLS, Firefox UA, cookies, Origin) got 406 for the grant too.
Cause still unknown. Hypotheses to separate: the edge looks at the body (VPN client id / scope), at the endpoint family (/oauth/*), at request headers, or at the network.

## Written by us (patch 0002, ideas taken from reading the other core, nothing copied)
- `controlplane/madshield_tls.go`: control-plane requests (account, Guardian, server list) start TLS with desktop Firefox's hello (uTLS; the same hello our data-plane code already had in package proxy, which cannot be imported from controlplane). HTTP/1.1; a hello the network refuses falls back to Go's TLS for that connection only (nothing sticky). Wired in `client.go` (`DialTLSContext` on the default and quick transports).
- `fxa/madshield_browser.go`: `BrowserTokens(session)` tries, one at a time and recording each answer: `token` (grant fxa-credentials), `authorization` + code exchange at oauth.accounts.firefox.com, the same two with the headers Firefox's own page sends (Origin, Referer, Sec-Fetch-*), then the edge challenge solver, then all four again. Non-406 answers (e.g. errno 104/138 = session not confirmed) come back unchanged. Hawk is written base64 (specification) and flips to the core's hex form for the process if the server answers 401. If every route fails: `StepsError` with the list and 4 labelled **probes** (session status; empty grant; grant with a wrong client id; grant with only the profile scope; none keeps a token) so the next report shows which attribute draws the 406.
- `service/madshield_browser.go` + route `POST /api/ms/signin-browser`: a sign-in session in the existing registry (polled with the usual `GET /api/signin/{id}`), loops while the page still asks for a code (error_code `waiting_confirm`), stores the account without a password, ends the session in the background (2 min cap). Failure code `blocked` carries the steps text.
- Kotlin: `FxClient.signInBrowser` -> that route; `FxWebSignIn.kt` shows `fx_web_blocked` (en/fa, our words, no other project's name) plus the steps line, `waiting_confirm` -> "confirm the sign-in".
- CI: Go core job (apply both patches, vet, test, build) green. Pure tests pass (a test now checks the patch has the route, the TLS hook and no "Arman VPN" text).

## Reading the next report
The red text lists steps, for example `token 406 (cache-fra...) | authorization 406 | ... | probe session status 200 | probe empty grant 400 | probe grant, other client 400 | probe grant, profile scope 200`.
- session status 200 but every grant 406 + profile-scope grant 200 -> the VPN scope/client is what is refused (policy); the network/IP is probably the lever.
- empty grant 406 too -> the whole /oauth/ family or request shape is refused: header/fingerprint work or another network.
- everything 406 including session status -> the signed-request family is refused from here.
